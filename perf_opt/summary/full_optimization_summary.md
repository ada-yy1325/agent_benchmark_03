## 二、阶段 1 · 性能画像（测了什么 → 发现了什么）

**测了什么**：2K/4K/8K 三档输入 × c1-c64 七档并发 = 20 点全矩阵。

**4K 主档数据**：

| 并发 | TTFT P50 | TPOT P50 | 输出吞吐 |
|:-----|:---------|:---------|:---------|
| c1 | 354.7 ms | 45.4 ms | 21.9 tok/s |
| c8 | 658.3 ms | 47.9 ms | 160.1 |
| c16 | 718.2 ms | 52.8 ms | 291.6 |
| c32 | 965.9 ms | 58.4 ms | 521.7 |
| c64 | **62 152.9 ms** | 58.4 ms | 525.4 |

**发现**：① 吞吐在 c32 饱和（~525 tok/s），c64 无增长——单组 TP8 算力到顶；② **c64 prefill 崩溃**（TTFT 62.2s，60 倍异常）；③ TPOT 全程稳健 → 瓶颈在调度。

## 三、阶段 2 · 预填充调度（改了什么 → 数值变化）

**测试**：扫 max-num-batched-tokens（2048/4096/8192/16384）+ 扫 max-num-seqs（32/48/64/128）。

| 优化项 | 结论 | 数值变化 |
|:-------|:-----|:---------|
| batched 扫描 | 8192 为 U 型谷底 = 原基线值 | **维持不变**（排除可调维度） |
| **max_seqs 32→64** | 核心优化 | **c64 TTFT 62 695→2 522 ms（−96%，25×）**；c64 吞吐 525→831 tok/s（**+58%**）；c32 代价 +7% TTFT |

阶段 2 是全程收益最大的一步：c64 从"不可用"变为"可批量"。清洗会话（10-19）复核：c64=2292.7ms/964.9 tok/s，结论成立（当时"final 验证"批次的 13.9s 系并发污染，已作废）。

## 四、阶段 3 · 并行拓扑（测了什么 → 结论）

**测试**：TP16 / DP2×TP8 原生 / DP4×TP4 / 双独立 TP8 / EP。

| 方案 | 结果 | 原因 |
|:-----|:-----|:-----|
| TP16 | ❌ 不可行 | shape 不兼容（模型加载 crash） |
| DP2×TP8 原生 | ❌ 不可行 | vllm-ascend 单节点 DP 设备分配 bug |
| DP4×TP4 | ❌ 不可行 | OOM（TP4 需 ~75GB/卡 > 64GB） |
| **双独立 TP8** | ✅ 唯一可行 | 卡0-7:8000 + 卡8-15:8001，客户端对半分流 |

**数值（清洗会话实测，每服务 64req）**：

| 并发 | 聚合吞吐 | vs 单服务 | 两侧失衡 |
|:-----|:---------|:----------|:---------|
| c32 | 1127.5 tok/s | **+98%（1.99×）** | 0.45% |
| c64 | 1885.0 tok/s | **+95%（1.95×）** | 1.6% |

## 五、阶段 4 · MTP 投机解码（最大反转）

**测了什么**：接受率摸底、MTP off/on 单变量、spec=2 尝试、多并发对比。

**坏模型上（原结论）**：接受率 4.35-4.73%（随机输入）/ 16.64%（自然文本）→ "MTP=OFF 更快"。

**好模型上（推翻）**：接受率 **95.79%**，MTP=ON 全面碾压：

| 并发 | 指标 | MTP OFF | MTP ON | 变化 |
|:-----|:-----|:--------|:-------|:-----|
| c1 | 吞吐 | 23.6 | **41.2 tok/s** | **+75%** |
| c1 | TPOT | 42.0 | **23.5 ms** | −44% |
| c8 | TTFT | 885 | **419 ms** | **−53%** |
| c8 | 吞吐 | 181.7 | **282.8** | **+56%** |
| c32 | TTFT | 1662 | **894 ms** | **−46%** |
| c32 | 吞吐 | 538.1 | **781.8** | **+45%** |

**结论**：坏模型"MTP=OFF"系量化损坏所致；**好模型生产建议 = MTP=ON**。spec=2 仍不支持（cudagraph shape 冲突，非量化问题）。

## 六、阶段 5 · 其他开关 + 精度复测（逐项结论与数值）

**5.3 additional config 单变量（坏模型实测相对收益）**：

| 开关 | 关掉/打开的后果 | 结论 |
|:-----|:----------------|:-----|
| cpu_binding | 关掉 → c32 TTFT **+34.3%** | **必开** |
| dsa_cp | 关掉 → 全局 TTFT **+18~35%** | **必开** |
| multistream_overlap | 关掉 → TTFT +1~3%，吞吐 −3~5% | 保留 |
| static_kernel | 坏模型上 +9~12% 吞吐；**好模型上仅 +1.3~1.7%** | 可开（收益小） |

**5.1 / 5.2 / 5.4**：

| 项 | 结论 | 数值 |
|:---|:-----|:-----|
| prefix caching | 随机负载无收益 | <1.5% 差异；真实共享前缀场景未测（已标注） |
| graph 模式 | eager 2.84× 慢（TPOT 129 vs 46ms）→ 止损；cudagraph/default/npugraph 差异 <2% | **取 cudagraph** |
| FP8 KV cache | 安全可用、性能中性 | <1.5% 差异 |

**5.5 精度（好模型）**：一致性（temp=0 确定性）✅ 全过；**GPQA 全量 141/198 = 71.21%**（历史好模型 72.22%，−1.4%，无显著回归）；npu16 重新量化模型文本+冒烟 3/3 验证通过。

## 七、最终对比建议（两套配置，好模型实测）

| 维度 | 低延迟交互版 | 高吞吐批量版 |
|:-----|:-------------|:-------------|
| 拓扑 | 单组 TP8EP8（8 卡） | 双独立 TP8（16 卡，客户端对半分流） |
| MTP | **ON**（接受率 95.8%） | OFF（双服务器 MTP 未实测，已标注） |
| graph / 调度 | cudagraph / batched 8192 / max_seqs 64 | 同左 |
| 开关 | cpu_binding+dsa_cp 必开；static_kernel ON；fp8 KV 可选 | 同左 |
| c1 | 330ms TTFT / 23.5ms TPOT / **41.2 tok/s** | — |
| c8 | **419ms** TTFT / 282.8 tok/s | — |
| c32 | 894ms / **781.8 tok/s** | 聚合 **1070.5 tok/s**（每服务 64req，失衡 <0.7%） |
| 适用 | 在线交互，c≤32 | 离线批量，甜蜜点 c32-64 |
| 代价 | c1 TTFT +3%（vs OFF） | TTFT 1.9s@c32（两服务各自排队） |

**启动命令**（可直接复制，启动器已指向 w8a8-npu16）：

```bash
# 低延迟交互版
ASCEND_RT_VISIBLE_DEVICES=0,1,2,3,4,5,6,7 python3 perf_opt/scripts/start_server_phase5.py \
  --port 8000 --mtp 1 --static-kernel true --kv-cache-dtype fp8 \
  --cpu-binding true --dsa-cp true --multistream-overlap true

# 高吞吐批量版（第二台同命令换卡 8-15、端口 8001、--mtp 0）
ASCEND_RT_VISIBLE_DEVICES=8,9,10,11,12,13,14,15 python3 perf_opt/scripts/start_server_phase5.py \
  --port 8001 --mtp 0 --static-kernel true --kv-cache-dtype fp8 \
  --cpu-binding true --dsa-cp true --multistream-overlap true
```
